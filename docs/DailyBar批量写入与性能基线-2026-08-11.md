# Daily Bar 批量写入与性能基线

关联 GitHub Issue：#42。

全市场批次按请求证券数完整记账。全部成功为 `succeeded`；至少一只成功、但有证券因
provider 失败或请求不可用而留下明确缺口时为 `partial`；请求非空且没有任何证券成功时
才是 `failed`。每只失败证券仍保留独立 ingestion 失败记录，成功证券的 Raw、Manifest、
质量结果和事实不回滚。Operations 同步记录请求、成功和缺口证券数，因此股票池可接受
同交易日的 `partial` 日行情工作流，但系统不会静默补齐缺失事实。

## 生产只读基线

2026-08-11 20:00（Asia/Shanghai）启动的 `daily_market` 在 21:16 仍处于 `daily_bar`
步骤。连续 12 秒观察完成 12 只证券，基线约为 **1.0 证券/秒**；当时累计 4,469 成功、
4 失败、1 正在处理，上市股票总数 5,208。失败率约 0.09%，均为明确的 Provider
归一化/请求错误。TDX 连接仍建立，数据库 `pg_blocking_pids` 为空，因此该次运行是缓慢但持续
前进，不是锁等待或重试死循环。

## 批量提交设计

- 每只证券仍独立创建 `ingestion.ingestion_run`，保留实际 provider、请求参数、Raw manifest、
  quality results 和事实 `ingestion_id`；不把多个 provider/run 合并成一个 lineage。
- Provider 请求、Raw 写入和验证完成后形成 `PreparedDailyBarBatch`。内存队列达到
  `DAILY_BAR_WRITE_BATCH_SIZE`（默认 100，范围 1..500）即提交，构成明确背压上限。
- 一个写批次在一个 PostgreSQL 事务内 executemany：Raw manifests、quality results、
  `core.daily_bar` upsert、各 ingestion run 终态。任一 SQL 失败时整批回滚并使工作流失败，
  不在未知数据库错误后继续制造部分成功。
- `core.daily_bar` 继续按 `(symbol, trade_date)` 幂等 upsert。提交前拒绝批内重复自然键、重复
  ingestion ID、错配 manifest/envelope/quality lineage。
- 批量流程预取本批任务的已知证券和交易日期集合，移除逐证券的两次引用完整性查询。
- 每次提交打印 position、runs、rows、事务耗时；外层仍报告完成位置、Provider 失败和
  unavailable 计数。

本改动不并发 Provider 请求，也不改变路由、Raw 格式、价格/单位、质量规则、调度时间或失败
可见性。默认 100 使 5,208 只证券的事实提交事务从约 5,208 次降至约 53 次；但每证券
ingestion run 的起始记录仍单独持久化。实际总耗时还受公共 TDX 响应时间限制，因此发布前只
承诺显著减少数据库往返，不承诺固定倍数。

## 其他任务只读审计

### 已确认

1. **Daily Bar（最高优先级，已处理）**：原流程每证券创建 run、查询证券/日期、提交 manifest/
   fact/run，生产基线证实约 1 秒/证券。
2. **可转债逐券日 K（中优先级）**：CLI 是单券命令，pipeline 每次独立 run/commit；当前未见
   日常调度中的全市场逐券循环。若未来增加批量/日调度，应复用同样的 prepare + bounded commit，
   现在不提前修改。
3. **Security、Trading Calendar、Stock Daily Indicator、Deducted Profit、Board Index、
   Classification（低优先级）**：Provider 一次返回集合，persistence 已用 executemany 在单事务
   提交；没有确认的逐证券数据库事务热点。
4. **开盘全市场竞价快照、收盘/集合竞价五档（低优先级）**：Provider 按协议上限分块取数，
   每个采集 attempt/session 将记录集合批量提交。按时间轮次提交是 Raw/观测语义边界，不应跨轮次
   合并。
5. **涨跌停股票池与衍生计算（低优先级）**：集合读取、纯计算后批量写快照/成员；未确认逐证券
   transaction。

### 假设与后续量测

- TDX 请求目前串行，批量数据库写入后网络延迟可能成为主要瓶颈。不能在没有端点限流、单一实际
  provider/endpoint lineage 和稳定性证据前直接并发；先上线本变更并比较 Provider 时间与 commit
  时间分布。
- `create_ingestion_run` 仍每证券一次事务，可能成为次级瓶颈。未来可设计“批量创建 running
  runs”，但必须保证崩溃恢复能看到已开始的每个请求，需独立 Issue/故障注入测试。
- 公共 TDX 节点池刷新本次仅 21/103 节点通过能力探测；这是上游可用性信号，不等价于数据库
  写入瓶颈。应分别监控端点成功率、切换次数和每证券请求耗时。

## 安全发布点

等待当前生产 `daily_market` 完成且后续依赖任务终态明确后，使用正常 release 流程部署；不要在
运行中替换 Worker。先以默认 100 运行一个交易日，比较总耗时、每批 commit 秒数、Provider
失败率、数据库连接/锁和 Raw/ingestion/core 数量一致性，再决定是否调整批大小或提出 Provider
并发方案。
