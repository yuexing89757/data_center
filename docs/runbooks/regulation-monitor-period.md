# 异动监控本期补算

依据 ADR-0063、Issue #87。`regulation-monitor.v3` 的本期起算日固定为
`2026-09-01`，不是每月自动重置。API 返回 `monitor_start_date` 和
`count_scope_label`，本期内次数仍是最近10个交易日的系统测算次数，不是交易所认定次数。

## 前置条件

- 通过受保护流程应用 `20260930000300_regulation_monitor_period.sql`。
- API 与 Worker 部署同一提交；不改变现有稳定采集源。
- 每日 ST 成功快照、证券生命周期、日 K、基准行情及相关规则就绪。
- 缺少事实的证券保留资料不足，不伪造行情，不强制清零为正常。
- 仅9月1日可使用空检查点；此后要求上一交易日同算法、同起算日的有效发布。

## 手工执行

使用正常 Worker 最小权限凭据，在项目运行目录执行现有命令。先检查 CLI 的
`regulation-monitor --help`，按日期逐日预检、执行；遇到失败停止后续日期。
已完成且输入未变的日期可幂等重跑。不要从7月重新补算，也不要删除旧批次。

长时间人工补算应启动独立、即时的后台进程并记录 PID、日期、状态、覆盖与耗时，
不能依赖交互 SSH 的存活。不得用 cron 等 OS 定时任务注册采集触发器。
日期截至最近已完成数据采集的交易日，不能提前计算当日未收盘数据。

## 验证

核对范围内每个交易日均有同起点的 v3 发布，且父检查点连续；检查资料不足原因，
并通过候选列表和单股监控接口核对起算日期与范围标签。正式公告数量独立验证。
若修改任一祖先日输入，其后代可能失效，必须从该日按交易日顺序补算。

原 v2 `RUNNING` 记录只有在核实没有对应运行进程、且未发布 monitor_context 后，
才允许调用现有失败标记方法处理；不删除其 Raw 或源事实。
