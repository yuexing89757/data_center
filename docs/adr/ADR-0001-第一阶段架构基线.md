# ADR-0001：第一阶段架构基线

- 状态：Accepted
- 日期：2026-07-27
- 决策者：项目所有者
- 适用范围：第一阶段 MVP

## 背景

项目代码已经清空并准备重新实现。为避免 IDE Agent 在数据源、标识、单位、存储和部署问题上自行猜测，本 ADR 固化第一阶段编码所需的最小决策。

## 决策

### 1. 第一阶段主数据源

使用 **BaoStock** 作为第一阶段唯一 Provider，覆盖：

- Security；
- Trading Calendar；
- Daily Bar。

第一阶段不实现 Router 和自动故障切换。Provider 必须把 BaoStock 字段转换成标准 DTO，BaoStock 字段不得进入 Pipeline、领域实体和数据库公共契约。

### 2. 证券统一标识

统一 `symbol` 格式：

```text
SSE:600000
SZSE:000001
BSE:920000
```

规则：

- 交易所使用 `SSE`、`SZSE`、`BSE` 标准代码；
- 证券代码按来源原始长度保留前导零；
- `symbol = exchange + ':' + code`；
- 来源标识如 `sh.600000` 只能存在于 Provider/Raw 边界；
- 跨表关联只使用 `symbol`，不使用裸 `code`。

### 3. Security 模型

第一阶段建立：

- `core.security`：当前证券身份和生命周期快照；
- `core.security_name_history`：名称有效期历史。

`core.security.status` 第一阶段只表达 `listed`、`delisted`、`unknown`。停牌属于 Market 的证券×交易日事实，不写入 Security 当前状态。

### 4. Trading Calendar 模型

第一阶段使用统一 A 股市场日历：

```text
market = CN_A_SHARE
```

主键为：

```text
(market, trading_date)
```

不在第一阶段分别维护 SSE/SZSE/BSE 日历。将来出现实际差异或扩展其他市场时，通过新 ADR 拆分。

### 5. Daily Bar 事实口径

第一阶段只保存**不复权日线事实**：

- 时区：`Asia/Shanghai`；
- 日期：交易所本地交易日；
- 价格：人民币元，数据库使用定点 `numeric`；
- 成交量：股，使用 bigint；
- 成交额：人民币元，使用定点 `numeric`；
- 涨跌幅：不作为权威来源事实，后续可由未复权价格计算；
- 主键：`(symbol, trade_date)`。

前复权、后复权和技术因子属于后续版本化 Derived 层，不进入第一阶段 Core Daily Bar。

### 6. Raw Store

第一阶段 Raw 文件保存在 **Worker 本地持久化目录**，格式为 Parquet/JSONL；不依赖 Supabase Storage。

路径规范：

```text
data/raw/<provider>/<dataset>/year=YYYY/month=MM/day=DD/<ingestion-id>.<ext>
```

Supabase 只保存 `ingestion.raw_manifest`，记录对象路径、SHA-256、采集参数、行数、Schema 版本和状态。Raw 目录必须独立备份，且不提交 Git。

### 7. 数据库与迁移

- 数据库使用自托管 Supabase PostgreSQL；
- 第一阶段查询接口使用 PostgREST；
- Schema 唯一来源是 `supabase/migrations/*.sql`；
- 不使用 Alembic 管理同一批表；
- ORM 不使用 `create_all()` 修改生产 Schema；
- CI 从空数据库执行全部 migrations；
- 生产 migration 通过受保护的 GitHub Environment Job 执行，并要求人工审批；
- 禁止通过生产 Studio 直接修改 Schema。

### 8. Python Worker 与调度

第一阶段 Python Worker 部署在自托管基础设施的独立进程/容器中，使用独立系统身份和数据库角色。

调度采用操作系统级定时器：

- Linux 使用 systemd timer，cron 作为可接受备选；
- GitHub Actions 不承担生产行情采集调度；
- 每个任务同时提供可手工执行的 CLI；
- 同一任务必须通过 advisory lock 或等价机制防止并发重复执行。

### 9. Supabase API 与安全

- Studio 仅用于管理，不作为应用 API；
- 客户端查询通过 Gateway 下的 PostgREST；
- 生产必须使用 HTTPS；
- 第一阶段对外契约放在 `api_v1` Schema 的只读 View/RPC；
- 内部 `ingestion`、`core`、`audit` Schema 不直接暴露；
- 客户端使用 publishable/anon 身份并受 RLS 限制；
- Python Worker 使用专用后端数据库角色，不把 secret/service key 暴露给客户端；
- 正式域名可以在部署 Issue 中确定，但 HTTPS 和入口隔离是硬约束。

### 10. API 版本策略

第一阶段稳定查询对象：

```text
api_v1.securities
api_v1.trading_calendar
api_v1.daily_bars
```

上层应用只依赖 `api_v1` View/RPC，不直接依赖 Core 表。破坏性变更通过 `api_v2` 发布，旧版本在明确弃用窗口内保留。

## 后果

### 正面

- IDE Agent 可以在不猜测核心口径的情况下编码；
- 第三方字段不会泄漏到 Pipeline 和 API；
- 未复权行情可作为稳定事实保存；
- PostgREST 契约与内部表结构解耦；
- 后续增加数据源、复权和 Metrics 时有明确扩展边界。

### 代价

- 第一阶段只有单数据源，不能自动故障切换；
- Raw 文件依赖 Worker 磁盘和独立备份；
- 名称历史与 API View 增加少量初始 Schema 工作；
- 自托管 Supabase 的备份、升级和安全仍由项目负责。

## 暂缓事项

以下内容明确不阻塞第一阶段开工：

- 第二数据源和 Router；
- Supabase Storage；
- 复权与因子；
- Capital、Classification、Metrics；
- FastAPI、MCP；
- 分钟线与实时行情。

它们进入开发前必须建立新的 ADR。
