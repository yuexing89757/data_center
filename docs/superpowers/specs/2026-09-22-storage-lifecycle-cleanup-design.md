# 存储生命周期与定时清理设计

- 日期：2026-09-22
- 状态：Approved（项目所有者于2026-09-22确认详设；尚未实现）
- GitHub Issue：[\#84](https://github.com/yuexing89757/data_center/issues/84)
- 关联：ADR-0006、ADR-0015、ADR-0017、ADR-0019、ADR-0050、ADR-0054、ADR-0058（Accepted）

## 1. 目标与现状

扩展既有 `data-cleanup-daily`，在不丢失历史来源事实、质量证据和重放能力的前提下降低磁盘增长。
继续使用 Worker 内 APScheduler，每天 03:00 Asia/Shanghai 执行，不增加操作系统定时任务。

2026-09-22 的只读基线：服务器磁盘约29 GB，使用71%，剩余约8.5 GB；当前 Raw 目录约6.1 GB，
项目发布目录约3.3 GB，生产数据库约5265 MB。数据库的 `audit.quality_result` 约1871 MB，
其中两条竞价提示规则各有2,665,053条记录。最近完整交易日的竞价 Raw 约174 MB/日。
9月21日三个 Raw 样本在内存中 gzip 后仅剩原大小的3.4%～3.5%；这不是所有数据集的压缩率承诺。
上述容量是不同统计口径，不能把数据库、目录和 Manifest 逻辑字节数直接相加推算可释放空间。

现有02:30归档与03:00清理正常执行。本方案不修订竞价采样、算法或API查询语义。

## 2. 方案选择和范围

采用“无损压缩与证据归档、明确白名单清理”。仅扩容不能抑制持续增长；按年龄直接删除 Raw 和
全部质量结果会破坏追溯。两者都不作为本次方案。仍须观察长期增长，压缩不等于无限容量。

| 数据/文件 | 本次规则 |
| --- | --- |
| 竞价在线序列快照 | 沿用最近三个已完成交易日，逐键确认历史归档后删除 |
| 竞价历史序列快照 | 沿用六个自然月，截止日当天保留 |
| 已登记 JSONL Raw | 原始内容长期保留；超过七个自然日后转换为无损 gzip 表示 |
| 指定两类竞价质量提示 | 新数据按批次汇总；旧逐行明细超过30个自然日后完整归档再删除在线明细 |
| 项目临时文件 | 仅清理本功能登记、所属任务已终态、超过七个自然日且不再被引用的临时文件 |
| 旧发布物 | 部署成功后独立清理，保护当前版本、两个回滚版本及依赖引用闭包 |

保留 `IngestionRun`、`RawManifest`、Session、Round、Operations、日K、龙虎榜、游资/席位、
股东人数、计算版本历史等事实。所有 ERROR、非白名单质量规则和已生成的汇总记录继续在线保留。
不按文件年龄删除未登记 Raw，不清理备份、系统日志、Docker、系统缓存或其他项目。
`core.stock_daily_indicator` 的现有保留流程不在此次改动范围内，不另加一个更短的清理窗口。

Issue #80 中“所有质量结果超过30天直接删除”的旧提案不是本次实现依据，不覆盖其历史讨论。

## 3. 既有职责与最小新增结构

- `LocalRawStore`：安全路径解析、gzip/JSONL读取、流式内容校验和不可变文件发布。
- 清理 Service：截止日、白名单、步骤编排、预算及失败处理；不把数据库SQL写入调度器。
- Persistence：候选分页、终态确认、归档登记及受限数据库删除事务。
- 竞价序列质量结果构造处：仅汇总本设计列出的非阻断提示；领域 Validator 不改变。
- Scheduler/Operations：仍使用 `data_cleanup`，为新增步骤记录独立结果和容量状态。
- 发布维护脚本：只管理项目发布根下的已识别发布物，不由 Worker 执行。

ordered migration 增加三个小型内部元数据表：

1. `ingestion.raw_compression`：一个 `raw_id` 对应一条已验证压缩表示，保存相对路径、gzip编码、
   压缩字节数、压缩文件SHA-256、校验时间和明文已移除的确认时间。只允许补记移除确认，不修改
   已登记内容身份。原 Manifest 的路径、原始SHA、原始字节数和行数不变。
2. `audit.quality_archive`：记录 `ingestion_id`、规则、格式版本、归档路径、压缩及内容SHA、
   字节数、条数、原记录创建时间范围与归档时间；同一批次和规则只接受一个相同内容的归档。
3. `operations.data_cleanup_report`：关联 WorkflowRun，保存本次截止点、分步骤行数/文件数/字节数、
   耗时、容量水位、剩余候选和错误码。不存凭据、来源响应或敏感绝对路径。

不新增公共接口、通用任务框架、对象存储依赖或动态目标表配置。优先使用标准库 `gzip`、`hashlib`、
`pathlib` 和已有数据库访问方式。Schema变更不得附带生产回填、文件压缩或清理。

## 4. Raw 压缩与读取协议

### 4.1 候选

以调度执行日上海零点减七个自然日为截止时刻，要求 Manifest 的 `created_at` 和关联采集运行的
`finished_at` 均严格早于截止时刻，运行已终态。只选已登记、本地、JSONL对象；失败/部分成功批次
也可无损压缩，但不能据此把批次改为成功。Parquet、缺文件和未登记对象不作推断式处理。
优先处理逻辑字节数较大的对象，以创建时间和raw_id确定稳定次序；不能为了压缩大量小文件而长期
推迟占空间最多的竞价Raw。已完成对象由压缩登记排除，明文移除尚未确认的对象进入恢复分支。

原逻辑路径 `provider/dataset/.../<id>.jsonl` 对应固定物理压缩路径 `<原路径>.gz`。
不创建第二个 RawManifest、不改 Raw 内容，不通过修改原 Manifest 哈希掩盖数据变化。

### 4.2 发布顺序与崩溃恢复

1. 获取清理单实例锁，读取候选并验证普通文件、受控根、无路径逃逸及软链接；拒绝未知已有文件。
2. 在同目录独占创建本次专属临时文件，以 gzip level 6、固定mtime流式压缩。验证原文件与
   Manifest 的字节数、SHA-256及行数，文件变化则终止。
3. flush/fsync后重新解压临时文件，验证解压后的字节、SHA及行数与原 Manifest 完全一致，并记录
   压缩字节数和SHA。解压长度最多为 Manifest 原始字节数加一，防止无限展开。
4. 原子发布到确定的 `.gz` 位置，不覆盖不同内容的已有文件。已有副本必须完整校验才能复用。
5. 数据库事务重新核对候选身份/终态，幂等登记已验证的压缩表示；相同 raw_id 但不同内容硬失败。
6. 登记提交后，再确认原文件身份未变和压缩副本可读，才移除未压缩副本并补记移除确认。
   登记前数据库故障时保留原件；移除后补记失败则下次验证压缩副本和明文确已不存在后补记。

中断最多留下两份或本次临时文件，不允许留下“数据库已指向不可用内容且原件已删”的状态。
已登记但明文未移除时，下次校验两者后继续；压缩文件已发布但未登记时，下次验证后登记。
未登记的可恢复归档文件不由临时清理猜测删除。

### 4.3 兼容读取

统一 Raw reader 优先尝试原路径；仅在不存在时尝试确定的 `.gz` 路径。读取到的内容仍必须按原
Manifest 校验，不能在原文件损坏时静默换另一份掩盖问题。并发移除原路径时允许重新打开压缩路径。
压缩表示有元数据登记便于选择和核对，读取器不因此获得数据库访问职责。
原写入器也必须把已存在的 `.gz` 视为同一逻辑对象已被占用，不能因为明文已移除，就允许相同
ingestion_id重新创建不同内容。原路径与压缩路径同时存在时，不覆盖任何一方。

盘点并适配重放、只读比较、恢复工具和手工修复工具的 Raw 读取路径；不得只修主重放命令。
竞价全市场 Raw 的“禁止自动重放”边界继续有效，支持压缩读取不代表启用竞价补采/重放。

## 5. 质量提示汇总与历史归档

白名单同时限定 `dataset_code=call_auction_market_series` 和以下规则/级别：

- `realtime_quote.lot_precision`：INFO；
- `realtime_quote.missing_source_timestamp`：WARNING。

不改变 Validator 的接受/拒绝判定、原 severity 或 failed 状态。新批次在生成持久化质量结果时，
按 ingestion、规则、severity、status、message 分组，保留 `finding_count`、全部受影响自然键
（含证券和原观察时刻）、固定 `aggregation_version`。只对这一白名单汇总；ERROR和其他提示逐条保存。
统计需区分“存储行数”和“原始finding数”，不得把两条汇总误报成只有两只股票受影响。

旧明细以 `created_at < 上海执行日零点 - 30个自然日` 为候选，关联 IngestionRun 必须终态。
仅处理未带汇总标记的白名单行。以 ingestion/规则为单位分页归档，完整保存每条原记录的全部字段，
包括质量ID、自然键、details、message及时间戳，按质量ID确定顺序，写入
`<Raw根>/_quality_archive/<ingestion_id>/<rule-code>/<content-sha>.jsonl.gz`。

先完整回读验证内容哈希、字节数、行数及精确质量ID集合；随后在同一数据库事务内锁定并重新比对
候选内容、登记归档、写入对应批次汇总，再只删除归档中的精确旧ID。任何差异均回滚数据库操作。
不按日期直接大范围DELETE；不存在或损坏的归档不得成为删除依据。
文件先于数据库提交，事务失败只会留下可安全重用的文件；已提交归档和汇总长期保留。

提供内部只读归档核验/读取能力，能按 ingestion 核对原记录并区分在线汇总与归档明细，不新增API。
数据库备份与独立文件备份需要同时包含归档登记和 `_quality_archive`，不能只备份数据库后声称
历史质量证据可恢复。

## 6. 临时文件和发布物的清理边界

临时清理仅覆盖本功能独占命名并有操作归属的暂存文件；开始写入前记录 operation_id、所属运行和
创建时间，成功后移出暂存区。只有所属任务已终态、已超过七天、已确认不是唯一可恢复副本才可删除。
身份无法确认的遗留文件只列在预览中。不能通过“没有 Manifest”认定文件是垃圾。
不递归扫描或删除 `/tmp`、用户主目录、工作区根、整个 Raw 根或共享缓存。

发布清理作为部署成功后的显式阶段，默认预览。受控发布元数据记录提交、发布时间、验证结果和
依赖位置，不以目录mtime决定成功版本。保护集合包含 Worker/API 当前目标、运行中进程的代码位置、
两个最近成功的不同回滚版本，以及这些版本递归引用的 `.venv`/共享运行时。
被引用的依赖所在旧发布目录整体保护；无法识别的旧目录、备份、含外置数据/配置的目录不自动删除。
执行前再次解析绝对路径并确认严格位于发布根内、不是根本身、没有变化或新增引用。
Worker的 `ProtectHome`、`ReadWritePaths` 和数据库最小权限不为删除发布物而放宽。

## 7. 调度、预算、预览和告警

03:00任务顺序：记录容量 → 原有在线/历史快照清理 → Raw压缩 → 旧质量明细归档清理 →
本功能临时文件清理 → 记录容量及汇总。保留原有归档缺失阻断门禁。
各步骤独立事务，已成功且可恢复的操作不因后一步失败而伪装回滚；WorkflowRun显式记录失败/部分完成。
个别缺失、损坏或不安全候选保留原状并记录稳定错误，独立候选可以继续，但该步骤不得报全成功；
数据库不可用、无法持锁或整体空间不足时停止新增写入。原有快照归档校验失败仍阻止其DELETE。

默认代码目录常量：每次最多30分钟，Raw最多10,000个实际压缩对象、审计最多100,000条原明细，
按200个候选分页；单个文件/归档工作单元最多256 MiB。SQL锁等待最多2秒、单语句最多30秒。
预算在分页、压缩和校验的流式分块间检查，超限不启动新单元、不删除未验证内容。单元中断可重试。
达到上限但仍有候选时记录 partial 和剩余量，次日从未完成候选继续，不从头反复只检查已完成数据。
这是协作式预算，不声称能够硬中断操作系统永久阻塞的文件I/O；异常超时需要运维告警而非强杀采集。

自动维护仅在03:00–04:00窗口开始；延迟触发越过窗口则记录未执行，不挤占09:15采集。
没有后台脱离Worker的压缩线程或新OS计划任务。手工执行同样遵守采集保护窗口09:10–09:40。

提供 `data-cleanup` 只读预览作为默认行为；真实执行须 `--execute --confirm`。预览只读数据库、
文件元数据及必要校验，不创建运行、目录、暂存、报告记录，不压缩、不删除；结果输出为脱敏JSON。
不允许传任意表名、路径通配符或保留期限。`.env`仍只用 `DATA_CLEANUP_ENABLED` 启停。

分别检查Raw/归档所在文件系统，按设备去重；使用率达到80%警告，达到90%或可用空间小于2 GiB严重
告警，写入结构化日志与持久报告，不擅自配置短信或邮件。写入暂存前至少有512 MiB可用，且足够覆盖
当前工作单元保守上界，否则不开始该单元；磁盘不足不能触发绕过校验的“紧急删除”。
统计报告不得把数据库DELETE行数换算为“已释放OS字节”，文件回收也以实际前后变化单独计量。

## 8. 权限、数据库空间和回退

有序migration授予上述内部元数据表所需最小权限，并将质量明细删除约束在白名单和已有归档证据内。
现有 `quality_result_worker_all` 是宽泛的permissive策略，新增DELETE不能仅叠加另一条permissive
白名单策略；应拆分原策略或增加RESTRICTIVE DELETE门禁，并用Worker角色实际验证ERROR和非白名单
行不可删除。原SELECT/INSERT能力保持不变。
不授予对其他表的DELETE或DDL；匿名、authenticated、API角色无内部归档读写权限。
不通过维护任务修改分区、执行 `VACUUM FULL` 或重建大表。

PostgreSQL逻辑删除使空间可复用，不保证立即归还OS。需要物理收缩时另行测量锁、临时空间和维护窗口，
取得明确授权后处理，不将整表重写塞进日常任务。

先部署和验证兼容reader、元数据migration及预览，再授权首次执行。启用压缩后，旧版只识别明文的
reader不能直接回滚运行；需选择兼容版本，或先通过受控、校验过的无损展开恢复明文且确认磁盘空间。
应用回退不删除压缩文件或归档，不对schema执行临时回滚SQL。

## 9. 验收和交付边界

- 单元：七天/三十天边界、时区、分页预算、采集保护窗口、容量阈值、白名单、affected keys与统计。
- 文件：原始字节一致、重复操作、空文件、损坏/截断、解压长度上界、软链接/目录逃逸、不同内容碰撞、
  磁盘不足、并发读、压缩后同一逻辑对象拒绝重写，以及每个文件发布/登记/删除边界的故障恢复。
- 审计：完整字段与精确ID一致、ERROR不删除、非白名单不变、事务失败保留明细、重复归档无丢失。
- 隔离PostgreSQL：ordered migration、约束、索引、RLS、最小权限、归档登记与删除原子性及报告事实。
- 回归：Raw replay/比较/恢复、竞价32轮、原在线归档校验、六个月保留、API合同不变。
- 发布清理：当前双服务不同版本、依赖位于旧目录、两个回滚版本、未知目录、引用变化及默认预览。
- 运行 ruff format/check、mypy、完整pytest及隔离数据库门禁，禁止使用生产库作集成测试。

详设已经确认，实施按同日的存储清理与发布物清理两个计划推进；计划中的代码和migration尚未交付。用户尚未授权本次
生产迁移、部署或首次生产清理。如发现Raw/数据库历史缺口，不通过本功能自动补造或掩盖。
