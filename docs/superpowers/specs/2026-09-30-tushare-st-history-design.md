# Tushare 历史 ST 快照补采设计

- 日期：2026-09-30
- 状态：待书面审阅
- Issue：#85
- ADR：ADR-0061（Proposed）

## 目标与范围

补齐从 2026-07-06 起的逐日 ST 适用性事实，让监管异动监控能够区分“确知非 ST”与
“ST 数据尚缺”。用户需要历史数据以支持连续监控计算；本次不产生交易建议或新的公开 API。
已批准独立 Tushare ST 日快照、Raw 血缘及既有 Worker 工作流复用。

## 选择与取舍

- 采用官方 `stock_st(trade_date=YYYYMMDD)` 的逐日完整名单。单日约数百行，直接表达
  监控需要的 ST 状态；2026-07-06 受控只读探测返回 211 行。
- 不用 `namechange` 推导全市场非 ST：变更记录不等于每股逐日完整名单；也不用当前名称
  倒填过去。
- 不给 pytdx 的 `core.daily_bar.is_st` 事后灌入另一来源，避免混合来源事实。

## 数据流

Tushare Provider 将 `stock_st` 响应保留为 Raw，映射 `ts_code` 到标准 `symbol`。
Validator 检查请求日期与全部行一致、代码格式/唯一性、非空以及少于官方 1000 行上限。
Persistence 在一个事务中写入该日完整快照及 IngestionRun/RawManifest 血缘；失败时只留下
失败审计，不发布完整覆盖。快照一行代表一个交易日，保存经排序且唯一的标准代码集合、
`source_code=tushare`、`ingestion_id` 和行数。重新采集同一天以新批次替换现行快照，旧 Raw
和运行记录保持不可变。Raw replay 重用相同映射与校验。

监控输入装配对每个目标交易日精确关联已发布快照：有快照且证券在集合内为 ST，有快照且
不在集合内为非 ST；缺快照或源数据失败为 `INSUFFICIENT_DATA`。非 ST 推断只建立在当日
完整覆盖上。证券名称继续用于展示，但不参与 ST 判定。快照 `ingestion_id` 进入计算输入身份；
更正后创建新版本并按交易日顺序重算后继链，旧结果不覆盖。

## 调度、补采与失败

日终 `regulation_daily_calculation` 现有 Worker 步骤先补当日 ST 快照，再计算监管状态。
历史范围仅按数据库交易日历逐日补采 2026-07-06 至 2026-09-29，跳过已验证的完整日期；
请求限时、有界重试、逐日记录成功/失败，不因单日失败把后续日标为完整。正式历史补算是
独立授权的后续步骤。

`daily_basic` 历史换手率使用现有 `stock-daily-indicators-bulk` 与 Raw replay，不建立第二条
采集路径。2026-09-30 受控探测中单股单日可返回，但全市场请求两次在限时内未完成；
大范围补采须先证实代理能返回完整单日响应。Core 仍只保留一个月，因此旧指标即使补采，
也只能在经授权的连续补算窗口内临时留存；Raw 保持可重放。

## 验收

- Provider 测试覆盖日期不符、重复/非法代码、空结果、1000 行疑似截断、上游失败及 Raw replay。
- 隔离 PostgreSQL 测试覆盖成功批次原子入库、重复日期、更正血缘、缺日不可推断非 ST、
  Worker 最小权限与 API 无内部表读取权。
- 监控测试覆盖 ST 排除、完整名单之外可适用、缺名单仍不足、输入更正后版本变化。
- 本地完整门禁通过后再考虑生产迁移与部署。生产验收逐日核对 RawManifest、快照覆盖与监控
  预检计数；不能因任务退出码为零就宣布全市场数据完整。

## 非目标

不改写既有日 K 或名称历史，不增加系统级调度，不变更公开契约，不自动发布历史计算批次，
不改变每日指标长期保留策略。
