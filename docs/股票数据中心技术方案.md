> 状态：讨论基线（待 ADR 逐项确认）  
> 初版日期：2026-07-15  
> v2 重写日期：2026-07-27

## 1. 文档目的

本方案定义股票数据中心重新开发时采用的技术架构、开发流程、数据分层和第一阶段范围。

v2 的关键变化：

- 数据库平台改为**自托管 Supabase**；
- 第一阶段**不建设 FastAPI**，查询先使用 Supabase PostgREST Data API；
- 数据采集、标准化、校验和计算继续由独立 Python Worker 承担；
- 数据库结构统一通过 SQL migration 演进；
- 开发采用 `需求/架构 → Issue → IDE Agent → PR → CI → 部署 → Wiki` 的闭环；
- 文档不保存密码、API Secret、JWT Secret 或数据库连接串。

本文描述目标架构，不把旧代码状态当作设计依据。若与旧部署文档冲突，以本方案和后续 ADR 为准。

---

## 2. 项目目标与边界

Market Data Center 是一个独立的证券数据产品，负责：

- 数据采集；
- 原始数据归档；
- 标准化与质量校验；
- 客观事实存储；
- 可复现的派生计算与统计；
- 通过稳定接口向上层应用提供数据。

第一阶段聚焦 A 股日频数据，优先完成一个可靠、可重放、可测试的最小闭环。

### 2.1 属于数据中心

- 证券基础信息；
- 交易日历；
- 日频 OHLCV；
- 数据来源与采集批次；
- 数据质量结果；
- 客观且可复现的派生数据。

### 2.2 不属于数据中心

- 情绪周期、冰点、高潮等主观解释；
- 主线题材和交易策略；
- 回测执行引擎；
- 面向具体上层产品定制的业务判断。

---

## 3. 核心设计原则

1. **事实优先**：先保存事实，再进行计算。
2. **原始可追溯**：保存来源、请求参数、采集时间和内容校验值。
3. **结果可重放**：标准事实和派生结果可从 Raw 层重新生成。
4. **来源隔离**：Provider 在边界内消化第三方字段、单位和编码差异。
5. **统一契约**：Pipeline 只接收标准化采集 DTO，不识别 BaoStock、AKShare 等来源字段。
6. **计算纯函数化**：Calculator 不访问数据库、不负责写入。
7. **计算版本化**：复权、因子及统计规则必须记录算法版本。
8. **Schema 即代码**：生产数据库结构只能由已提交、已审查的 migration 修改。
9. **默认最小权限**：客户端访问依赖 API Key 和 RLS；管理密钥只存在于后端 Secret 中。
10. **渐进建设**：先完成单数据源闭环，再扩展多源 Router、指标和 MCP。

## 4. 总体架构

```text
外部数据源
交易所文件 / BaoStock / AKShare / 其他来源
        │
        ▼
Python Worker
Provider → Raw Store → Normalize → Validator → Calculator → Persistence
        │
        ▼
自托管 Supabase
├── PostgreSQL       标准事实、派生数据、统计和运行记录
├── PostgREST        第一阶段查询 API
├── Auth + RLS       身份与行级访问控制（按需启用）
├── Storage          小规模在线 Raw 文件（可选）
└── Studio           管理入口，不作为应用 API
        │
        ▼
脚本 / 看板 / 上层应用 / 后续 MCP
```

### 4.1 组件职责

| 组件 | 职责 | 明确不负责 |
| --- | --- | --- |
| Provider | 调用外部来源并转换成标准采集 DTO | 不写数据库、不计算指标 |
| Raw Store | 保存不可变的来源响应和采集元数据 | 不提供领域查询 |
| Validator | 检查结构、范围、唯一性和跨字段一致性 | 不静默修正严重错误 |
| Calculator | 由事实确定性计算派生结果 | 不读写数据库 |
| Persistence | 事务、幂等写入和冲突处理 | 不包含来源解析逻辑 |
| Supabase PostgreSQL | 保存标准事实和查询结果 | 不运行重型 Python 计算 |
| PostgREST | 第一阶段标准查询接口 | 不承载复杂工作流和批处理 |
| Studio | 数据库管理与观察 | 不作为客户端地址或业务后台 |

## 5. 技术选型

| 类别 | 第一阶段选择 | 说明 |
| --- | --- | --- |
| 语言 | Python 3.12 | 数据采集与处理主语言 |
| 包管理 | uv | 锁定依赖和可复现环境 |
| 配置 | pydantic-settings | 环境变量校验，不提交 Secret |
| 数据处理 | Pandas + PyArrow | 先减少技术栈；确有性能需求再引入 Polars |
| 数据库 | 自托管 Supabase PostgreSQL | 核心事实与查询存储 |
| 数据库访问 | SQLAlchemy 2.x + psycopg 3 | Worker 的事务与批量写入 |
| Schema 迁移 | Supabase 风格 SQL migrations | 数据库结构唯一事实来源 |
| Raw 格式 | Parquet / JSONL | 表格型用 Parquet，非稳定结构用 JSONL |
| API | Supabase PostgREST | 第一阶段不建 FastAPI |
| 测试 | pytest | 单元、契约和集成测试 |
| 代码质量 | Ruff + mypy | 格式、静态检查和类型检查 |
| CI/CD | GitHub Actions | PR 检查及受控部署 |
| 文档 | Markdown + ADR + LLM Wiki | Wiki 只记录已合并落地的事实 |

### 5.1 第一阶段明确不引入

- FastAPI；
- Prefect Server；
- 多数据源自动故障切换；
- MCP Server；
- 分钟线、tick 数据；
- 全量指标平台；
- 与 Supabase 功能重复的第二套数据库迁移系统。

这些能力只有在出现明确需求和验收标准后才通过 ADR 引入。

## 6. Supabase 的定位

当前使用的是**自托管 Supabase**，不是 Supabase Cloud。

### 6.1 服务入口必须分开理解

| 入口 | 用途 | 是否提供给应用 |
| --- | --- | --- |
| Studio | 管理数据库、观察 Schema | 否，仅管理员 |
| REST `/rest/v1/` | PostgREST Data API | 是 |
| Auth `/auth/v1/` | 登录与 JWT | 按需 |
| Storage `/storage/v1/` | 文件访问 | 按需 |
| PostgreSQL | Worker、迁移和备份 | 仅后端/运维 |

Studio 与 API 可能经过同一个 Gateway 暴露，但它们的认证方式和用途完全不同。部署文档必须记录实际路由，不能根据端口猜测。

### 6.2 自托管责任

以下能力由项目自行负责：

- Docker Compose 运行与版本升级；
- 数据库备份、恢复和恢复演练；
- TLS、域名、反向代理和防火墙；
- 日志、监控、磁盘和容量告警；
- API Key、JWT、数据库密码和 Studio 凭据轮换；
- 数据库 migration 的生产部署；
- 故障响应。

不得在方案中假定 Supabase Cloud 的 Branching、托管备份、PITR 或 Preview Project 可用。

### 6.3 环境变量分类

仓库只提供 `.env.example`，且只能出现占位符：

```dotenv
# 对外 API
SUPABASE_URL=http://<supabase-api-gateway>
SUPABASE_PUBLISHABLE_KEY=<client-safe-key>

# 仅后端任务
SUPABASE_SECRET_KEY=<server-only-secret>
DATABASE_URL=postgresql+psycopg://<user>:<password>@<host>:<port>/<database>

# CI/CD
MIGRATION_DATABASE_URL=postgresql://<migration-role>:<password>@<host>:<port>/<database>
```

Studio Basic Auth、数据库密码、API Secret、JWT Secret 不得写入 GitHub Issue、PR、Wiki 或仓库文件。

## 7. 数据库与 Schema 管理

### 7.1 Migration 是唯一事实来源

建议目录：

```text
supabase/
├── config.toml
├── migrations/
│   ├── <timestamp>_create_ingestion.sql
│   ├── <timestamp>_create_security.sql
│   ├── <timestamp>_create_trading_calendar.sql
│   └── <timestamp>_create_daily_bar.sql
└── seed.sql
```

规则：

1. 每个 Schema 变更必须生成 migration；
2. migration 与对应代码在同一个 PR 中审查；
3. 禁止通过生产 Studio Table Editor 或 SQL Editor 直接改变 Schema；
4. CI 必须从空数据库执行全部 migration；
5. 已在生产执行的 migration 原则上不可修改，只能追加修正 migration；
6. 破坏性迁移必须包含备份、兼容窗口和回滚/前滚说明；
7. ORM 不调用 `create_all()` 管理生产表。

### 7.2 Schema 分区建议

```text
public       对外允许查询的稳定表和视图
ingestion    采集批次、来源文件和运行状态
core         标准事实
derived      可重算派生结果
metrics      客观统计结果
audit        数据质量与审计日志
```

PostgREST 默认暴露范围必须显式配置。内部 Schema 不应因为建表而自动成为公共 API。

### 7.3 RLS 原则

- 对客户端可访问的表默认启用 RLS；
- publishable/anon 身份默认只读；
- 写入由 Python Worker 使用服务端身份或专用数据库角色完成；
- service/secret key 永不进入浏览器；
- 管理表、采集日志和 Raw 清单默认不向客户端开放；
- RLS policy 与表结构一样进入 migration 和代码审查。

## 8. 数据分层

### 8.1 Raw：来源原始层

保存外部来源的原始响应，原则上不可变、不可覆盖。

建议路径：

```text
raw/<provider>/<dataset>/year=YYYY/month=MM/day=DD/<ingestion-id>.parquet
```

数据库保存 Raw Manifest，而不是把所有原始内容重复塞入 JSONB：

```text
ingestion_id
provider
dataset
object_path
content_hash
request_params
fetched_at
row_count
schema_version
status
```

### 8.2 Core：标准事实层

第一阶段核心事实：

- `security`：证券身份及生命周期；
- `trading_calendar`：市场交易日历；
- `daily_bar`：不复权日频 OHLCV；
- `ingestion_run`：采集批次；
- `data_quality_result`：质量检查结果。

标准事实应记录 `source`、`ingestion_id`、`created_at` 和必要的版本信息，但不在每行复制完整来源响应。

### 8.3 Derived：派生层

派生层包含可由事实重新计算的结果，例如：

- 复权价格；
- 收益率；
- 移动平均；
- 后续市值与涨跌停判定。

派生结果至少记录：

```text
algorithm
algorithm_version
input_data_version / ingestion watermark
calculated_at
```

### 8.4 Metrics：统计层

第一阶段暂不建设完整 Metrics，只保留 Schema 边界。待 Capital、Classification 和规则模型准备完成后再开始市场统计。

## 9. Provider 与标准化契约

### 9.1 按能力拆分接口

不采用不断膨胀的统一大接口。Provider 按数据集能力实现一个或多个契约：

```text
SecurityProvider
TradingCalendarProvider
DailyBarProvider
CapitalProvider          （后续）
ClassificationProvider   （后续）
```

### 9.2 Provider 输出标准 DTO

Provider 内部完成：

- 来源字段映射；
- 证券代码规范化；
- 日期与时区规范化；
- 数值单位转换；
- 来源特有枚举转换；
- 缺失值语义转换。

Pipeline 只接收标准 DTO。以下代码属于架构违规：

```python
# 禁止在 Pipeline 中出现来源字段
row["pctChg"]
row["isST"]
row["code_name"]
```

原始响应在转换前写入 Raw Store，标准 DTO 保留 `source` 和 `ingestion_id` 以便追溯。

### 9.3 第一阶段只实现一个主源

先选择一个能完成 Security、Trading Calendar、Daily Bar 的主数据源，完成稳定闭环。第二数据源接入前，必须先具备：

- Provider 契约测试；
- 相同数据集的交叉校验规则；
- 冲突记录方式；
- Router 的健康和降级语义；
- 数据来源优先级 ADR。

## 10. API 策略

第一阶段不建设 FastAPI。

### 10.1 对外查询

简单查询通过 Supabase PostgREST 提供：

- 证券列表和详情；
- 指定市场、日期范围的交易日历；
- 指定证券、日期范围的日 K；
- 后续稳定的只读视图。

客户端面向稳定 View 或 RPC，不直接依赖内部表结构。表重构时优先保持 View 契约兼容。

### 10.2 何时引入 FastAPI

满足以下任一条件时再提交 ADR：

- 需要跨 PostgreSQL 与 Parquet 的统一查询；
- 需要复杂领域编排；
- PostgREST/RPC 难以表达查询契约；
- 需要独立缓存、限流或协议转换；
- MCP 需要稳定的服务端领域接口；
- 不希望继续让数据库 View/RPC 承担 API 契约。

### 11.1 Issue 必备内容

- 背景与目标；
- 明确不在范围内的内容；
- 数据/接口契约；
- 数据库影响；
- 验收标准；
- 测试要求；
- 关联 ADR。

### 11.2 PR 必备内容

- 关联 Issue；
- 改动摘要；
- Schema 与 API 兼容性；
- migration 执行和回滚/前滚说明；
- 测试证据；
- 安全影响；
- 文档更新。

### 11.3 CI 门禁

```text
ruff format --check
ruff check
mypy
pytest
从空库执行全部 migrations
Provider 契约测试
数据库集成测试

```

CI 默认使用临时数据库，不允许普通 PR 工作流连接生产数据库。生产 Secret 应放在受保护的 GitHub Environment 中，并限制到部署 Job。

### 11.4 LLM Wiki 原则

- Issue 记录“计划做什么”；
- PR 记录“实际改变了什么”；
- CI 证明“当前实现能工作”；
- Migration 记录“数据库如何演进”；
- Wiki 记录“系统现在是什么”。

Wiki 更新发生在 PR 合并后。未确认的提案必须标记为 Draft，不能写成当前架构事实。

## 12. 部署、备份与安全

### 12.1 生产部署顺序

```text
检查备份
  → 执行向后兼容 migration
  → 验证 Schema/PostgREST
  → 部署 Python Worker
  → 运行 smoke test
  → 记录发布结果
```

涉及删除列、改类型等破坏性操作时，采用 expand/migrate/contract，多次发布完成，不在一次部署中直接破坏旧消费者。

### 12.2 备份

自托管 Supabase 的备份由项目负责：

- 定期 PostgreSQL 逻辑备份；
- 数据量增大后增加物理备份/WAL 归档；
- Storage/Raw 对象单独备份；
- 备份保存到 Supabase 主机之外；
- 定期执行恢复演练；
- 记录 RPO、RTO、保留周期和最近恢复验证时间。

未经过恢复验证的备份不能视为可靠备份。

### 12.3 安全底线

- 对外入口使用 HTTPS，不允许生产 API 长期裸 HTTP；
- Studio 不应直接暴露给所有公网来源；
- 禁止提交 `.env`、数据库连接串和任何 Secret；
- 已出现在聊天、文档、Issue 或 Git 历史中的密码必须轮换；
- PostgreSQL 端口不直接暴露公网，或严格限制来源；
- 后端使用独立最小权限数据库角色；
- 定期轮换 Studio、数据库、API 和 JWT 相关密钥；
- 开启 GitHub Secret scanning 和依赖安全检查。

## 13. 第一阶段 MVP

第一阶段目标不是实现六大领域，而是证明整条工程和数据链路可靠。

### 13.1 交付范围

1. 初始化 Python/uv 工程；
2. 建立 Supabase migrations 和本地测试数据库；
3. 建立 `ingestion_run` 与 Raw Manifest；
4. 实现 Security 标准模型与表；
5. 实现 Trading Calendar 标准模型与表；
6. 实现未复权 Daily Bar 标准模型与表；
7. 接入一个数据源 Provider；
8. 实现 Raw 保存、标准化、校验和幂等入库；
9. 建立 PostgREST 只读 View 和 RLS；
10. 建立单元测试、Provider 契约测试和数据库集成测试；
11. 建立 GitHub Issue/PR 模板与 CI；
12. 建立生产 migration、备份和 smoke test 流程；
13. 合并后更新 LLM Wiki。

### 13.2 MVP 验收标准

- 从空数据库可完整执行全部 migration；
- 同一采集批次重复执行不会产生重复事实；
- 任一标准行可以追溯到来源和 Raw 对象；
- 非法数据不会进入 Core 表，并能查到质量失败原因；
- PostgREST 能按证券和日期范围查询日 K；
- anon/publishable 身份不能写核心事实表；
- CI 在 PR 中自动完成所有检查；
- 生产库可以从备份恢复到一个独立环境；
- 文档和实际 Schema 一致。

### 13.3 第一阶段之后

按实际需求依次评估：

1. 复权因子与版本化派生行情；
2. 第二数据源、交叉校验和 Router；
3. Capital；
4. Classification；
5. Metrics；
6. FastAPI；
7. MCP。

| 决策 | 第一阶段结论 |

## 15. 当前结论

第一阶段采用：

```text
Python Worker
+ 自托管 Supabase PostgreSQL/PostgREST
+ SQL migrations
+ Parquet/JSONL Raw Store
+ GitHub Issues/PR/Actions
```
