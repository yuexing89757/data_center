# 最小生产发布运行手册

本文定义可立即打包的最小发布范围：一个 `market-data-center worker` 进程、自托管
PostgreSQL、仓库内有序 migration，以及持久化 Raw 和 scheduler 目录。PostgREST、
FastAPI 和 MCP 都不属于本次最小发布；操作系统级
采集计划任务和生产数据均不进入发布包。

## Linux 发布物

在干净且已经通过评审的提交上执行：

```bash
uv sync --all-groups --locked
uv run python scripts/build_release.py --platform linux
```

产物为 `dist/market-data-center-<version>-linux.tar.gz` 及其 `.sha256` 校验文件。在发布
主机解压前运行 `sha256sum -c market-data-center-<version>-linux.tar.gz.sha256`。归档只包含当前提交的 Git 跟踪
文件，不包含 `.env`、Raw、备份、日志、虚拟环境或凭据。发布主机需要 Python 3.12、
`uv`、访问 PostgreSQL 的网络能力，以及到公共 TDX 节点端口的出站网络能力。

在发布主机解压到一个临时版本目录，验证归属后切换到 `/home/project`。使用
`uv sync --no-dev --locked` 创建生产虚拟环境。把
`deploy/linux/market-data-center.env.example` 复制为 `/home/project/.env`，从
密钥管理器填值并设为 `0600`；创建 `/var/lib/market-data-center/raw`、
`/var/lib/market-data-center/scheduler` 和节点池文件所在目录，归属 `market-data-center`
用户并保持可写。`PYTDX_POOL_PATH` 使用持久化绝对路径；1 小时刷新周期固定在受控代码
目录中。Linux 不挂载
本地通达信目录。Worker 在持锁后、启动调度器前刷新统一能力节点池，刷新失败时使用最后一个
有效池；新旧池均不可用则拒绝启动。发布 smoke 只读校验池格式和 quote/SSE/SZSE 必需能力，
不连接行情服务器，也不写池文件。本项目的生产模板保持全市场竞价序列和收盘五档任务开关为
`true`；`.env` 不配置任务 hour/minute/second/cadence/batch。上线时必须在只读管理页再次核对全部
启用任务及其固定计划。`call-auction-market-snapshot-daily` 和 `call-auction-snapshot-daily` 均已
移除，不得另建替代 cron、systemd timer 或 Windows Task Scheduler。两个公共竞价接口固定读取
09:25:20 序列末批。2026-09-07 起序列最后四轮固定为
09:24:20、09:24:40、09:24:53、09:25:20；第30轮批次码为 `092453`。

复制 `deploy/linux/market-data-center-worker.service` 到 `/etc/systemd/system/` 后执行
`systemctl daemon-reload`。首次启用或重启服务属于生产变更，必须得到明确授权；获授权后
仅启用这个 Worker 单元，不创建 cron 或 timer，也不启动 FastAPI。

## 上线前门禁

以下每项都必须有当次发布的操作记录；本地打包或 CI 测试不能替代生产证据：

1. 记录要发布的 Git 提交和版本，确认工作树干净且完整本地门禁通过。
2. 使用 `scripts/backup_restore.py` 创建 PostgreSQL 应用数据备份，单独备份 Raw，并在隔离数据库完成
   恢复演练和快照比对。未验证的备份不算发布门禁通过。
3. 确认 Worker 与 migration 使用不同的最小权限凭据；完成计划中的凭据轮换，
   验证新凭据有效、旧凭据失效。不得把值写入发布记录。
4. 确认生产 PostgreSQL 不向公网任意来源开放，Raw、scheduler 与节点池目录持久化且可写，
   公共 TDX 节点端口可达，并且只有一个 Worker 实例。公共节点可能限流、下线或缺少 BSE；
   启动门禁要求 quote、SSE 和 SZSE 能力，业务需要 BSE 时另行核对池中的 BSE 能力数量。
5. 先运行 GitHub `Production migration and smoke check` 的 `check` 模式。只有已批准的
   migration 窗口才可运行 `apply`；它是唯一生产 schema 变更路径。
6. 先在隔离数据库应用 `20260814000700_create_call_auction_market_series.sql` 和
   `20260817000200_add_auction_series_value_semantics.sql` 并通过集成检查；在受保护
   生产 migration 窗口应用后，确认父表及当月至未来分区存在。初始分区只覆盖至 2027-09-30，必须在
   2027-09 前通过新的 ordered migration 创建后续月份。

## 发布与只读验收

停止旧 Worker，保存其日志和版本；安装新包并保留外置 `.env`、Raw、scheduler 状态。
启动后依次执行：

```bash
sudo --preserve-env=MIGRATION_DATABASE_URL,DATABASE_URL \
  sh deploy/linux/smoke-check.sh /home/project
```

脚本要求 systemd 单元存活，并以只读模式检查 PYTDX 节点池、Worker、migration/schema、
基础事实和 lineage；它不会探测行情节点、`api_v1`、PostgREST 或任何 HTTP API。再确认日志
无重复实例或阻断级质量错误，且
`http://127.0.0.1:8765/admin/scheduled-tasks` 只在本机可访问。
确认 JobStore 显示 09:15 的 `call-auction-market-series`，且不显示已退役的
`call-auction-market-snapshot-daily`；序列任务属于 `morning_auction`。

不要为了冒烟验证手工触发生产采集。等待下一交易日的目录内调度完成 live gate：先确认Producer在
32个计划点都发起了Provider采集并写出Raw、数据库有32个明确终态Round且没有缺失sample sequence，
每轮冻结全集一致；确认最后四轮为09:24:20、09:24:40、09:24:53、09:25:20，
第30轮deadline为09:25:20且最后deadline为09:25:40；确认单Writer按序完成、没有重复Worker，并检查
partial/missed、endpoint attempt、Raw Manifest和质量结果。数据库慢时Session可以在09:25:40后完成，
但Round `collected_at`必须保持来源采集完成时间。抽查09:25前item的 `value_semantics=auction_indicative`，确认
价/量/额分别为买一价、买一股数及两者乘积（买一缺失时三者均为空），并确认 09:25 后为
`opening_trade`；再检查 09:25:20 末轮的 WorkflowRun、JobExecution、所选 IngestionRun、Raw
manifest、质量结果、实际批次数、失败证券数和 endpoint attempt 数；并确认只读任务页不显示已退役
的 09:25:30 和 21:30 jobs。不得为验证而
补造或补采历史交易日，也不得手工替代已移除的自动最终化。满足这些证据前，不得把该行为表述为已经在生产运行。

竞价序列在线事实保留最近 12 个完整月份，Raw/Manifest 长期保留。分区创建与淘汰只能通过受评审的
ordered migration：先创建未来分区并验证备份，再在维护窗口 drop 超龄分区。Worker、APScheduler 和
`.env` 不承担任何分区 DDL。

## DragonTiger 历史覆盖修复（Issue #70）

本节只适用于 ADR-0053 对应的受控发布。项目所有者已明确要求本次不创建数据库备份，因此本次发布
不得调用 `backup_restore.py`，上文“上线前门禁”第 2 项由该书面授权替代；其余只读预检、精确目标
核对、隔离数据库 migration/集成测试和生产健康检查仍不可跳过。

发布顺序固定如下：

1. 在隔离可丢弃数据库应用并验证
   `20260908000200_repair_dragon_tiger_historical_coverage.sql`，确认旧函数签名不存在、新四个 RPC
   存在且内部表没有授予 `market_data_api` 直接读取权限。
2. 通过受保护的 production migration workflow 先 `check` 后 `apply`；不得手工执行 DDL。
3. 部署同一 Git 提交的 Worker 与 FastAPI，保持两个数据源任务关闭，先验证 `/healthz`、`/readyz`
   和 Worker 本地任务页。
4. 完成 Tushare/Eastmoney 权利、凭据和网络预检后，将外置环境中的
   `SECURITY_BSE_ENABLED=true`、`DRAGON_TIGER_ENABLED=true`，重启单一 Worker 并确认 20:15/20:30
   两项受控任务存在；不得创建 cron 或 timer。
5. 先执行 `market-data-center --provider tushare security-bse`。再执行
   `market-data-center dragon-tiger-raw-recovery --dry-run`；审阅限定目录和校验结果后才可执行
   `market-data-center dragon-tiger-raw-recovery --execute --confirm`。
6. 对已登记且可重放的失败 ingestion ID，逐个先运行
   `market-data-center raw-replay --ingestion-id <uuid> --dry-run`，验证通过后再去掉 `--dry-run`。
7. 从 `core.trading_calendar` 只读确定运行时最近一个已收盘的 `CN_A_SHARE` 交易日，执行：

   ```bash
   market-data-center dragon-tiger-collect \
     --start-date 2025-01-01 --end-date <latest-closed-trading-date> \
     --confirm-eastmoney-source-terms-reviewed
   ```

   命令范围上限为 730 个自然日，会跳过已成功日期并在单日失败后继续；退出码非零时保留并审阅
   JSON 摘要中的 `failed_dates` 和 `quality_code_counts`，不得把部分覆盖报告为成功。
8. 最终按交易日核对成功 run、Raw manifest、Event/SeatTrade 数量和质量码，再对最近十个已收盘
   交易日逐日查询新 RPC；确认结果无 `period_type`，触发窗口与金额周期分离，单侧披露和质量码
   可见。剩余缺口按稳定错误码报告，不用旧日期或空成功补造。

## 回退

应用回退只切回上一个已验证的软件包并重启单一 Worker。SQL migration 默认只前进；不得
临时手写回滚 SQL。若 schema 或数据异常，停止 Worker，按已演练的恢复方案在明确目标上
恢复，再重复 migration check 和 smoke check。任何恢复、凭据轮换或生产 migration 都需要
用户明确授权。
