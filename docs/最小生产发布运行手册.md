# 最小生产发布运行手册

本文定义可立即打包的最小发布范围：一个 `market-data-center worker` 进程、自托管
PostgreSQL、仓库内有序 migration，以及持久化 Raw 和 scheduler 目录。PostgREST、
FastAPI 和 MCP 都不属于本次最小发布；操作系统级
采集计划任务和生产数据均不进入发布包。

## Linux 发布物

在干净且已经通过评审的提交上执行：

```bash
uv sync --all-groups --locked
uv run python scripts/build_release.py --platform linux
```

产物为 `dist/market-data-center-<version>-linux.tar.gz` 及其 `.sha256` 校验文件。在发布
主机解压前运行 `sha256sum -c market-data-center-<version>-linux.tar.gz.sha256`。归档只包含当前提交的 Git 跟踪
文件，不包含 `.env`、Raw、备份、日志、虚拟环境或凭据。发布主机需要 Python 3.12、
`uv`、访问 PostgreSQL 的网络能力，以及到公共 TDX 节点端口的出站网络能力。

在发布主机解压到一个临时版本目录，验证归属后切换到 `/home/project`。使用
`uv sync --no-dev --locked` 创建生产虚拟环境。把
`deploy/linux/market-data-center.env.example` 复制为 `/home/project/.env`，从
密钥管理器填值并设为 `0600`；创建 `/var/lib/market-data-center/raw`、
`/var/lib/market-data-center/scheduler` 和节点池文件所在目录，归属 `market-data-center`
用户并保持可写。`PYTDX_POOL_PATH` 使用持久化绝对路径；12 小时刷新周期固定在受控代码
目录中。Linux 不挂载
本地通达信目录。Worker 在持锁后、启动调度器前刷新统一能力节点池，刷新失败时使用最后一个
有效池；新旧池均不可用则拒绝启动。发布 smoke 只读校验池格式和 quote/SSE/SZSE 必需能力，
不连接行情服务器，也不写池文件。本项目的生产模板保持集合竞价五档、全市场竞价序列、收盘五档和
09:26 全市场开盘竞价来源四个任务开关为 `true`；`.env` 不配置任务 hour/minute/cadence/batch。上线时必须在只读管理页再次核对全部启用
任务及其固定计划，特别是 `CALL_AUCTION_SNAPSHOT_ENABLED` 只启用工作日 09:26 的
`call-auction-market-snapshot-daily`。`call-auction-snapshot-daily` 已移除，不得另建替代 cron、systemd
timer 或 Windows Task Scheduler。09:26 任务只从单个 endpoint 形成完整的 SSE/SZSE listed-stock
来源快照，BSE 暂缓，最多两次完整尝试，09:29:30 后不再发起请求。

复制 `deploy/linux/market-data-center-worker.service` 到 `/etc/systemd/system/` 后执行
`systemctl daemon-reload`。首次启用或重启服务属于生产变更，必须得到明确授权；获授权后
仅启用这个 Worker 单元，不创建 cron 或 timer，也不启动 FastAPI。

## 上线前门禁

以下每项都必须有当次发布的操作记录；本地打包或 CI 测试不能替代生产证据：

1. 记录要发布的 Git 提交和版本，确认工作树干净且完整本地门禁通过。
2. 使用 `scripts/backup_restore.py` 创建 PostgreSQL 应用数据备份，单独备份 Raw，并在隔离数据库完成
   恢复演练和快照比对。未验证的备份不算发布门禁通过。
3. 确认 Worker 与 migration 使用不同的最小权限凭据；完成计划中的凭据轮换，
   验证新凭据有效、旧凭据失效。不得把值写入发布记录。
4. 确认生产 PostgreSQL 不向公网任意来源开放，Raw、scheduler 与节点池目录持久化且可写，
   公共 TDX 节点端口可达，并且只有一个 Worker 实例。公共节点可能限流、下线或缺少 BSE；
   启动门禁要求 quote、SSE 和 SZSE 能力，业务需要 BSE 时另行核对池中的 BSE 能力数量。
5. 先运行 GitHub `Production migration and smoke check` 的 `check` 模式。只有已批准的
   migration 窗口才可运行 `apply`；它是唯一生产 schema 变更路径。
6. 先在隔离数据库应用 `20260814000700_create_call_auction_market_series.sql` 和
   `20260817000200_add_auction_series_value_semantics.sql` 并通过集成检查；在受保护
   生产 migration 窗口应用后，确认父表及当月至未来分区存在。初始分区只覆盖至 2027-09-30，必须在
   2027-09 前通过新的 ordered migration 创建后续月份。

## 发布与只读验收

停止旧 Worker，保存其日志和版本；安装新包并保留外置 `.env`、Raw、scheduler 状态。
启动后依次执行：

```bash
sudo --preserve-env=MIGRATION_DATABASE_URL,DATABASE_URL \
  sh deploy/linux/smoke-check.sh /home/project
```

脚本要求 systemd 单元存活，并以只读模式检查 PYTDX 节点池、Worker、migration/schema、
基础事实和 lineage；它不会探测行情节点、`api_v1`、PostgREST 或任何 HTTP API。再确认日志
无重复实例或阻断级质量错误，且
`http://127.0.0.1:8765/admin/scheduled-tasks` 只在本机可访问。
确认 JobStore 显示 09:15 的 `call-auction-market-series`，以及
09:26 的 `call-auction-market-snapshot-daily`；前两个属于 `morning_auction`，09:26 仍属于默认 executor。

不要为了冒烟验证手工触发生产采集。等待下一交易日的目录内调度完成 live gate：先确认竞价序列有
32 个明确终态 Round、每轮冻结全集一致、最后 deadline 为 09:25:40，并检查 partial/missed、endpoint
attempt、Raw Manifest 和质量结果；抽查 09:25 前 item 的 `value_semantics=auction_indicative`，确认
价/量/额分别为买一价、买一股数及两者乘积（买一缺失时三者均为空），并确认 09:25 后为
`opening_trade`；再检查 09:26
WorkflowRun、JobExecution、完整 `succeeded` IngestionRun、Raw manifest、质量结果、实际批次数、
总耗时、失败证券数和 endpoint attempt 数；并确认只读任务页不显示已退役的 21:30 job。不得为验证而
补造或补采历史交易日，也不得手工替代已移除的自动最终化。满足这些证据前，不得把该行为表述为已经在生产运行。

竞价序列在线事实保留最近 12 个完整月份，Raw/Manifest 长期保留。分区创建与淘汰只能通过受评审的
ordered migration：先创建未来分区并验证备份，再在维护窗口 drop 超龄分区。Worker、APScheduler 和
`.env` 不承担任何分区 DDL。

## 回退

应用回退只切回上一个已验证的软件包并重启单一 Worker。SQL migration 默认只前进；不得
临时手写回滚 SQL。若 schema 或数据异常，停止 Worker，按已演练的恢复方案在明确目标上
恢复，再重复 migration check 和 smoke check。任何恢复、凭据轮换或生产 migration 都需要
用户明确授权。
